# Выкладка «единого каталога» FTask (подготовлено 2026-09-13, ничего не задеплоено)

Затронуто три системы и два репо. **GitHub push ничего не делает с базой и Edge Function** —
в `faim-kreo-web` нет CI вообще (только GitHub Pages для статики), в `CreatorBot` Actions
деплоит только бота. Миграция и Edge — отдельные ручные шаги.

## Что выкладывать

| Слой | Что | Как |
|---|---|---|
| **БД** | `supabase/migrations/20260912225648_ftask_catalog.sql` | Supabase MCP `apply_migration(name="ftask_catalog", query=<файл>)` или SQL Editor. Идемпотентна. Dry-run в транзакции с `rollback` уже прогонялся на проде без ошибок. |
| **Edge** | `supabase/functions/kreo-api/index.ts` + `logic.js` → **v14** | MCP `deploy_edge_function(name="kreo-api", entrypoint_path="index.ts", verify_jwt=false, files=[index.ts, logic.js])`. Оба файла обязательно (деплой затирает набор). |
| **Бот** | `CreatorBot` (kreo.py, bot.py, тесты, доки) | commit + push `main` → Actions деплоит на VPS + `systemctl restart creatorbot`. |
| **Фронт** | `faim-kreo-web` (index.html, css/, js/, tests/, доки) | commit + push `main` → GitHub Pages (~1 мин). Пользователям: полностью закрыть и открыть `/app` (кеш WebView). |

## Порядок

1. **Миграция БД.** Ничего не ломает старому фронту/Edge v13: только новые nullable-колонки и
   две новые таблицы. После — `get_advisors(type=security)`: новые таблицы под RLS (service_role
   в обход), RPC `set_creo_niches` — только service_role.
2. **Edge v14.** Совместим со СТАРЫМ фронтом: все прежние actions на месте, `bootstrap` лишь
   добавляет поля (`niches`, `niche_ids`, `source_*_url`). Единственное поведенческое изменение,
   заметное старому фронту: кнопка «Работа» (`set_creo_status in_progress claim=true`) на чужом
   крео теперь отдаёт 409 `already_claimed` вместо перехвата — это и есть фикс B.
   Если деплоить Edge ДО миграции — bootstrap не падает (ниши пустые), но `set_creo_niches`/
   `create_niche` вернут 500 до миграции.
3. **Бот.** Пуш → Actions. Новый `source_prep_loop` до миграции молчит (400 на неизвестную
   колонку → `log.debug`), после — начинает готовить исходники: 3 крео за 30 с, старые записи
   подтянутся сами (`source_state IS NULL`). Условный PATCH `sent` и миграция legacy-чекпоинта
   работают без схемы.
4. **Фронт.** Пуш → Pages. Новый фронт НЕ работает со старым Edge v13 полноценно (нет
   `niches`/`defer`/`set_notes` → тосты «Не вышло»), поэтому строго после шага 2.

Итого безопасная последовательность: **БД → Edge → бот → фронт.** Между шагами можно жить
сколько угодно.

## Проверки после выкладки

- Открыть `/app`: каталог, вид «Свободные», у референсов с фото — превью (появятся по мере
  работы `source_prep_loop`; до этого «готовится…»). `journalctl -u creatorbot | grep "kreo source"`
  — строки `крео #N → ready/none/too_big`.
- Двумя аккаунтами нажать «Взять» на одном крео → у второго «уже взял другой», исполнитель первого.
- Карточка: видео играет внутри, «Исходник в Telegram» открывает сообщение; заметка сохраняется
  и видна второму человеку через ≤10 с; ниша создаётся и фильтрует; «Отложить» → «Отложенные» → «Вернуть».
- Загрузить второй результат к готовому крео → в Ready уходит только новый файл; в карточке он первым.
- Админ → Ниши: переименовать/удалить (крео остаются).
- `kreo_delivery.json` на VPS: если в нём были записи старого формата — в логе `сконвертирован` либо
  DM владельцу «старый прогресс не совпадает» (тогда проверить Ready руками и удалить запись).

## Откат

- **Фронт:** `git revert` / вернуть предыдущий коммит Pages — старый фронт работает с Edge v14.
- **Edge:** повторный `deploy_edge_function` с содержимым v13 (в git до этого коммита) — старый
  фронт снова «перехватывает» кнопкой «Работа» (то есть баг B вернётся). Новый фронт с v13 — нет.
- **Бот:** revert коммита → предыдущая версия; `source_*` колонки просто перестанут заполняться.
- **БД:** миграцию НЕ откатывать: колонки nullable, таблицы никому не мешают. Если очень нужно —
  `drop table creo_niches, niches; alter table creos drop column source_paths, …` (ручной SQL),
  но после этого Edge v14 будет отдавать пустые ниши, а бот — 400 в `source_prep` (тихо).
- Данные: `sources/<id>/…` и `previews/<id>/src_*` в Storage при откате остаются (место на free-плане!).

## Ограничения, о которых стоит знать

- Bot API отдаёт файлы только ≤20 МБ → тяжёлые видео-референсы остаются «открыть в Telegram» (`too_big`).
- Storage free-плана ~1 ГБ: исходники не ретеншенятся — при заполнении добавить sweep (как `retention_sweep`).
- Ссылки, скачанные ботом ДО этой версии, не имеют `file_id` → `source_state='none'`, превью не будет.
- Заметки — last-write-wins; одновременная правка двумя людьми одной заметки перезапишет более раннюю.
