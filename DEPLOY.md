# Выкладка «единого каталога» FTask (подготовлено 2026-09-13, ничего не задеплоено)

## Дополнение: пачки видео и «Планирование» (2026-09-17, локально)

Изменения этого раздела **не применялись к production, не деплоились и не пушились**.
Безопасный порядок выкладки обязателен: **БД → Edge → CreatorBot → фронт**.

1. Применить `supabase/migrations/20260917195825_delivery_batches.sql`. Она создаёт
   `delivery_batches`, `delivery_batch_items`, индексы/lease-поля, RLS и атомарный RPC
   `update_delivery_batch`. Таблицы закрыты для `anon`/`authenticated`; доступ имеет
   `service_role` через Edge и бот.
2. Задеплоить Edge Function `kreo-api` вместе с **обоими** файлами `index.ts` и `logic.js`.
   Проверить actions `delivery_list/create/update/refresh_sources/send_now/cancel/retry_failed/redeliver`.
3. Затем задеплоить CreatorBot с `batch_delivery.py` и обновлённым `bot.py`. До миграции и
   Edge новый фронт не выкладывать; бот без таблиц будет лишь логировать ошибки очереди.
4. Последним выложить фронт (`index.html`, `css/app.css`, `js/`, включая `js/delivery.js`).
   Версия статических ресурсов: `20260918a` (18.09: галочки на всех видео + закреплённая панель
   выбора, только фронт). Полностью закрыть и снова открыть Telegram Mini App.

После выкладки проверить вручную: одну немедленную пачку из 1 файла; пачку 2–10 файлов как один
альбом документов и сохранение порядка; отложенную доставку с реальным часовым поясом; изменение
версии/уровня до отправки; перезапуск бота во время подготовки; ошибку одного файла и точечный
retry; состояние `delivery_unknown` без автоматического повтора. Наблюдать журнал по
`creatorbot.batch_delivery`, строки таблиц и локальные receipts в `tmp/delivery_receipts`.

Откат приложения: сначала вернуть фронт, затем Edge и бот. Таблицы сразу не удалять: остановленный
старый код их не использует, а удаление уничтожит очередь/историю. Подготовленные объекты
`deliveries/...` также оставить до отдельного согласованного retention-процесса.

## Дополнение: скачивание исходников на устройство (2026-09-13)

Локально закончено после остановки Claude по лимиту; **не закоммичено, не запушено,
не задеплоено**. CreatorBot в этой задаче не менялся. Прежде чем выкладывать, проверить
фактическую версию сервера: сведения о каталоге ниже описывают предыдущую подготовку,
а не подтверждают текущий production.

- Сначала обновить **Edge `kreo-api`**, включая `index.ts` и `logic.js`: новый `sign_download`
  принимает `{id, field: "source"|"media"|"result", index: <integer>}`. Авторизация и членство
  обязательны; путь берётся из массива крео, произвольный путь клиент не передаёт.
  Возвращает свежий signed attachment URL на 600 секунд. Bucket остаётся приватным.
- Затем выложить фронт: `index.html`, `css/app.css`, `js/` (включая **новый `download.js`**).
  Версия ресурсов `20260913c`. Старый Edge не знает `sign_download`, поэтому порядок важен.
- Новая миграция **не нужна**. Но уже существующая миграция каталога и подготовка `source_paths`
  ботом должны быть выложены, иначе исходников в Storage не будет. Если каталог ещё не выкладывали,
  следовать общей последовательности БД → Edge → бот → фронт ниже, используя актуальные файлы.

Поведение: у свободного/рабочего референса есть ⬇, у альбома открывается карточка со скачиванием
каждого файла; «Взять» для скачивания не требуется. Исходник остаётся после загрузки результата.
Готовые результаты скачиваются тем же способом. Отмена Save As не запускает fallback. Ошибка
записи вызывает abort; выбранный существующий файл **никогда не удаляется**. Null-слоты signed
URL сохраняют индексы файлов, обновление URL не подменяет выбранный файл.

Папка: в поддерживаемом безопасном Chromium-контексте вызывается `showSaveFilePicker` прямо
в обработчике клика, с постоянным `id=ftask-downloads`, без `startIn: downloads`. Последнюю
папку запоминает браузер для этого ID; это не путь в localStorage. В Telegram WebView API может
быть недоступен/запрещён — тогда native `downloadFile` или браузерная загрузка; **папку и её
запоминание FTask в этих режимах не контролирует**. Подтверждение Telegram не выдаётся за факт
записи файла. Никакого обхода авторизации для открытия полного FTask в браузере не добавлено.

Проверено локально: `tests/run.html` — **58 passed, 0 failed** при 1440×1000 (`?split=1`)
и 500×900; `deno check --no-lock supabase/functions/kreo-api/index.ts` — успешно (Deno 2.9.6).
`tests/download-tests.js` проверяет контракт доступа, индексы альбома, имена, вызов picker до
сети, постоянный ID, отмену, ошибки HTTP/потока, сохранность старого файла, повторные клики,
изменение файла в открытом диалоге, fallback и обновление превью. Сеть/OS/Telegram замоканы.

**После выкладки вручную:** на реальном ПК скачать исходник в нестандартную папку; скачать
второй и проверить стартовую папку; закрыть/открыть FTask и повторить. Отдельно проверить в
Telegram Desktop и на телефоне, какой режим доступен. Отмена не должна ничего скачивать;
в альбоме каждый файл должен соответствовать выбранному; после результата исходник остаётся.
Нативный Save As и реальный Telegram WebView в этой задаче не проверялись.

Существующие ограничения подготовки исходников остаются: Bot API ≤20 МБ, старые ссылки без
сохранённого `file_id`, квота Storage, асинхронная очередь подготовки. Текст не имеет файла;
для недоступного исходника показывается состояние и ссылка на Telegram.

Затронуто три системы и два репо. **GitHub push ничего не делает с базой и Edge Function** —
в `faim-kreo-web` нет CI вообще (только GitHub Pages для статики), в `CreatorBot` Actions
деплоит только бота. Миграция и Edge — отдельные ручные шаги.

## Порядок

1. **Миграция БД.** Ничего не ломает старому фронту/Edge v13: только новые nullable-колонки и
   две новые таблицы. После — `get_advisors(type=security)`: новые таблицы под RLS (service_role
   в обход), RPC `set_creo_niches` — только service_role.
2. **Edge v14.** Совместим со СТАРЫМ фронтом: все прежние actions на месте, `bootstrap` лишь
   добавляет поля (`niches`, `niche_ids`, `source_*_url`). Единственное поведенческое изменение,
   заметное старому фронту: кнопка «Работа» (`set_creo_status in_progress claim=true`) на чужом
   крео теперь отдаёт 409 `already_claimed` вместо перехвата — это и есть фикс B.
   Если деплоить Edge ДО миграции — bootstrap не падает (ниши пустые), но `set_creo_niches`/
   `create_niche` вернут 500 до миграции.
3. **Бот.** Пуш → Actions. Новый `source_prep_loop` до миграции молчит (400 на неизвестную
   колонку → `log.debug`), после — начинает готовить исходники: 3 крео за 30 с, старые записи
   подтянутся сами (`source_state IS NULL`). Условный PATCH `sent` и миграция legacy-чекпоинта
   работают без схемы.
4. **Фронт.** Пуш → Pages. Новый фронт НЕ работает со старым Edge v13 полноценно (нет
   `niches`/`defer`/`set_notes` → тосты «Не вышло»), поэтому строго после шага 2.

Итого безопасная последовательность: **БД → Edge → бот → фронт.** Между шагами можно жить
сколько угодно.

## Проверки после выкладки

- Открыть `/app`: каталог, вид «Свободные», у референсов с фото — превью (появятся по мере
  работы `source_prep_loop`; до этого «готовится…»). `journalctl -u creatorbot | grep "kreo source"`
  — строки `крео #N → ready/none/too_big`.
- Двумя аккаунтами нажать «Взять» на одном крео → у второго «уже взял другой», исполнитель первого.
- Карточка: видео играет внутри, «Исходник в Telegram» открывает сообщение; заметка сохраняется
  и видна второму человеку через ≤10 с; ниша создаётся и фильтрует; «Отложить» → «Отложенные» → «Вернуть».
- Загрузить второй результат к готовому крео → в Ready уходит только новый файл; в карточке он первым.
- Админ → Ниши: переименовать/удалить (крео остаются).
- `kreo_delivery.json` на VPS: если в нём были записи старого формата — в логе `сконвертирован` либо
  DM владельцу «старый прогресс не совпадает» (тогда проверить Ready руками и удалить запись).

## Откат

- **Фронт:** `git revert` / вернуть предыдущий коммит Pages — старый фронт работает с Edge v14.
- **Edge:** повторный `deploy_edge_function` с содержимым v13 (в git до этого коммита) — старый
  фронт снова «перехватывает» кнопкой «Работа» (то есть баг B вернётся). Новый фронт с v13 — нет.
- **Бот:** revert коммита → предыдущая версия; `source_*` колонки просто перестанут заполняться.
- **БД:** миграцию НЕ откатывать: колонки nullable, таблицы никому не мешают. Если очень нужно —
  `drop table creo_niches, niches; alter table creos drop column source_paths, …` (ручной SQL),
  но после этого Edge v14 будет отдавать пустые ниши, а бот — 400 в `source_prep` (тихо).
- Данные: `sources/<id>/…` и `previews/<id>/src_*` в Storage при откате остаются (место на free-плане!).

## Ограничения, о которых стоит знать

- Bot API отдаёт файлы только ≤20 МБ → тяжёлые видео-референсы остаются «открыть в Telegram» (`too_big`).
- Storage free-плана ~1 ГБ: исходники не ретеншенятся — при заполнении добавить sweep (как `retention_sweep`).
- Ссылки, скачанные ботом ДО этой версии, не имеют `file_id` → `source_state='none'`, превью не будет.
- Заметки — last-write-wins; одновременная правка двумя людьми одной заметки перезапишет более раннюю.
